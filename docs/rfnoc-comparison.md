# RFNoC短记录汇聚：项目架构对照与复现

本项目实现支持固定帧静态水位准入和有界变长完整帧准入的AXI4-Stream仲裁器，接口与通用验证范围见[工程说明](../README.md)。
RFNoC案例采用完整帧模式，比较本工程核心、帧FIFO加轮询和仅按帧轮询三种汇聚结构，评估已有包门控下的缓存代价与保护边界。

在固定24 B、每源等待ACK、原有完整包门控的合法业务中，**仅按帧RR方案更省LUT且延迟更低**，
未观察到第二层完整帧缓存的应用收益。该结果限于所列业务和配置，不构成新算法、普遍最优或真实系统实测结论。

## 比较边界

冻结UHD `d1be63490e3f3df22ff2f4ea1315f9aada468562`，以真实`radio_tx_core`的欠载逻辑产生24 B通知：
两拍头、两拍时间戳、一拍操作字、一拍错误码。来源80MHz，控制100MHz。三个方案共同保留：

```text
radio事件 → 原32项事件FIFO → 原CtrlPort序列化/等待ACK → 原CDC
          → 原32拍terminal packet gate → 候选4→1汇聚 → 消费/ACK模型
                                      原反向CDC ← 3拍ACK
```

真实源每路只允许一笔待应答事务。原`axi_packet_gate`在收齐包后释放，保持其默认元数据缓冲配置。
endpoint保留原双向功能、512字从请求缓存及原异步FIFO；7系列XPM的异步RAM最少32拍，不能把请求SIZE=1写成实际两拍。
未修改vendor FIFO/CDC或源代码。消费者独立检查6拍格式、来源、序号、时间戳、操作字和错误码，
输出完成后200ns开始发送合法3拍ACK，经原反向CDC返回；200ns是固定参考模型，非真实主机时延。

| 候选 | 额外汇聚结构 | 候选自身存储槽 | 末级完整帧/长度检查 |
| --- | --- | ---: | --- |
| `native`，本工程 | 4/32/16，RR，PACKET=1，M=6，KEEP=0 | 64拍 | 完整帧后出流；第6拍无LAST报错停接 |
| `frame_fifo`，强帧缓存基线 | 相同RAM深度，帧FIFO+RR，M检查器计入 | 74拍 | 完整帧后出流；标记坏帧/超长丢弃，见尾回收 |
| `rr_only`，仅按帧轮询基线 | 仅原`axis_arb_mux`按帧RR | 6拍：每路1拍+共享2拍 | 可边接收边出流，无额外M检查或帧提交 |

外部实现固定verilog-axis `48ff7a7e2ef782cf778d47910cf85835c64b1bce`。帧FIFO开启`FRAME_FIFO`、
`DROP_OVERSIZE_FRAME`、`DROP_BAD_FRAME`，关闭`DROP_WHEN_FULL`、RAM/输出附加流水选项；KEEP关闭时DEPTH=16表示16拍RAM。
仅RR方案不加第二层FIFO或预知故障标记，但保留原仲裁器所有弹性寄存器。三方均使用原source/gate，
这是同一合法业务需求下的架构比较，**不是等总容量算法比较，也不是完整RFNoC N×N控制网络替换**。

## 实验与证据来源

对照共使用17份轨迹：两个帧缓存候选各含五个场景及竞争负载2.5ns时钟相位，共12份；
仅RR候选含四类合法场景及竞争2.5ns相位，共5份。
其中12份帧缓存轨迹来自已有归档，经hash核验后复用；5份仅RR轨迹单独生成。
复用时核对源/vendor/核心、激励、READY/ACK政策及对应包装分支保持一致。
分析器统一核算全部17份轨迹，检查外生事件身份、产生时刻、复位日程一致，并报告交付交集及各自独有记录。

每份轨迹固定观察12000控制周期，稀疏、竞争、有限背压和过载负载采用确定性释放计划，不使用实机采集流量。
同一主记分板按真实输入/输出握手逐拍核对数据、LAST、来源、顺序、不混帧及背压稳定，
RR每源最多3个待输出拍的队列边界也检查。分析器仅对两个帧缓存候选要求“提交不晚于首拍输出”；
RR仍必须满足输入首拍先于输出首拍、输入尾拍不晚于输出完成，以及相同ACK政策。
所有场景观察结束均无未完成遗留；源满丢失、复位作废和交付分别入账，分析保留全部记录。

## 合法业务延迟与丢失：参考仿真

下表相位0，单位ns；均值仅针对各自交付记录，顺序均为**本工程 / 帧FIFO基线 / 仅RR**。

| 场景 | 生成数 | 完成数 | 源FIFO丢失数 | 事件产生至输出完成均值ns |
| --- | ---: | --- | --- | --- |
| 稀疏单源 | 8 | 8 / 8 / 8 | 0 / 0 / 0 | 401.250 / 421.250 / 351.250 |
| 四源竞争 | 96 | 96 / 96 / 96 | 0 / 0 / 0 | 7764.063 / 8056.250 / 7142.396 |
| 有限下游背压 | 96 | 96 / 96 / 96 | 0 / 0 / 0 | 8650.625 / 8923.542 / 7916.250 |
| 有限过载 | 320 | 151 / 150 / 152 | 169 / 170 / 168 | 12886.879 / 13271.783 / 12002.105 |

稀疏记录的候选首拍接受至输出完成为**120 / 140 / 70ns**。两个帧缓存方案尾拍接受至首拍输出为20/40ns；
仅RR为−30ns，表示首拍已经提前出流，并非负等待。该指标在JSON中明确叫`tail_accept_to_first_output`，
只有前两方案另有`commit_to_first_output`。不能把提前首拍和完整帧准入当作同一种保护承诺。

前三类无丢失，全部相同身份记录的RR完成时刻都更早。竞争下较本工程平均早621.667ns；
差值包含后续事件排队和ACK闭环累积，不全是单次仲裁延迟。2.5ns相位的竞争均值为7751.563/8043.750/7129.896ns，
本工程与RR仍差621.667ns；这仅是一项相位敏感性检查，不是CDC可靠性证明。

过载必须比较相同记录：三方共同交付138条，其事件至完成均值为11884.438/12307.917/11000.236ns。
对这138条，RR分别平均早884.203ns和1307.681ns，且逐条更早。本工程另交付13条、RR另交付14条；
帧FIFO基线另交付12条、RR另交付14条。前两方案之间共同交付141条，独有10/9条。
所以“总完成数多1或2条”不等于在完全相同交付集合上多收一两条。未把小样本P99或观测最大值当作硬时延上界。

## 故障保护与恢复边界

| 边界/条件 | 两个完整帧候选 | 仅RR |
| --- | --- | --- |
| 原gate之前没有收齐包 | 共同原gate阻止该包出流 | 同一原gate保护；正常业务共享这一保证 |
| gate之后人为抹去尾拍 | 第二层完整帧准入阻止该故障帧输出 | 可能已输出前缀并持续持有授权；没有额外完整帧拦截保证 |
| 第6拍无LAST | 本工程停接；帧FIFO基线告警并待尾回收 | 无M检查/告警；不能解释为检查通过 |
| 真实故障发生率及系统恢复 | 未取得实际故障与恢复需求 | 同样缺项；不能从不等价保护承诺排性能冠军 |

仅RR候选不运行gate后失尾场景；脚本与测试台均明确拒绝该组合，未测得其恢复数字。
以下诊断只比较两个帧缓存候选：gate后、候选前抹去源0第三条记录TLAST，
源等不到ACK，基线也等不到后续尾拍。按预定第400周期全路径复位100ns，复位前80周期统一关闭READY。
这是人为边界诊断，不是已采集的硬件故障，也没有测gate前截断。

| 失尾诊断结果 | 本工程 | 帧FIFO基线 |
| --- | ---: | ---: |
| 生成/完成/源丢失/复位作废 | 288 / 46 / 112 / 130 | 288 / 45 / 113 / 130 |
| 其中健康路复位作废 | 97 | 97 |
| 故障成交至可观测告警 | 10ns | 10ns |
| 故障至预定复位等待 | 1855ns | 1805ns |
| 复位释放至故障路首条新事件完成 | 715ns | 735ns |

人工复位等待不是自动恢复速度，715/735ns包含新事件释放与公共路径。复位后两边4×8条新事件均完成并收到ACK。
没有观察到本工程恢复机制优势；仅清仲裁FIFO不会解除源端等待ACK，恢复需要全路径协调。

## 复现与验证

依赖Python3.12、Vivado2025.2及官方XPM/unisim，完整长期回归另需Icarus；入口支持Windows/WSL，
`VIVADO_ROOT`可指定安装目录。实现使用仓库内`registered_context.tcl`、`clock.xdc`和`report_reference.tcl`，
运行前复制到`build/rfnoc/impl/reference/`，并在`manifest.json`记录来源及副本的SHA256。
不依赖Git、提交编号或历史对象；普通克隆与源码ZIP使用相同入口，仍需安装工具和取得外部依赖。
上述结果对应各自归档的实验输入；重新运行时以实际生成的文件hash记录输入，结果单独保存并核对。
UHD文件按各自LGPL/GPL声明取得，verilog-axis为MIT；依赖清单含许可与逐文件SHA256。Vivado模型不复制入仓库。

```sh
python3 scripts/fetch_axis.py             # 首次下载；缓存后--check离线核验
python3 scripts/fetch_uhd.py
python3 scripts/rfnoc_compare.py prepare  # 准备参考脚本并记录文件hash，不启动Vivado
python3 scripts/rfnoc_compare.py sim      # 相位0：两帧缓存候选各5场景，RR仅4合法场景
python3 scripts/rfnoc_compare.py sim --scenario contended --phase-ps 2500
python3 scripts/rfnoc_compare.py analyze
python3 scripts/rfnoc_compare.py analyze --scenario contended --phase-ps 2500
python3 scripts/rfnoc_compare.py impl     # 三候选参考实现
python3 scripts/rfnoc_compare.py source   # 公共单源OOC综合
python3 scripts/run.py all --events
```

可用`--candidate native`、`--candidate frame_fifo`或`--candidate rr_only`选择单个候选。
分析前须准备所选候选与相位的完整轨迹；默认分析三方时需要三方数据。
生成物在`build/rfnoc/`；每次新运行保存源hash，逐事件CSV、逐候选汇总与全部候选成对比较分别留存。
分析输出包含候选字典与`pairs`，包括三方共同交付集合统计；负的尾拍至首拍间隔不裁零。
原始实验日志、输入hash、复用核验记录与物理报告另行归档，未随本源码仓库提供。

5份仅RR轨迹检查通过，12份复用轨迹的统一分析及独立逐拍/ACK审计通过。
工程完整回归已有162项长期仿真与13项预期参数拒绝通过的记录，37份合法编译日志为空。
RFNoC案例的验证范围为仿真、公共单源综合和汇聚部分参考实现，未包含独立形式化证明、真实主机采集、上板或全系统时序签核。

## 项目结论与适用范围

在已有完整包门控、固定短记录且每源等待ACK的业务下，增加第二层完整帧缓存未体现实际收益。
本工程核心提供明确契约下的帧准入功能；该案例说明选择汇聚结构时需结合上游缓存、容量、延迟与故障保护需求。
比较结果支持上述范围内的架构取舍，不证明新算法、最优缓存配置或普遍的新颖性。

仍缺真实主机ACK分布与实机业务/故障轨迹、实际可接受损失和恢复接口、全系统时序与上板、
更多来源契约及任意流量证明。RFNoC实际业务固定6拍整字，不为本核心变长/TKEEP功能提供真实需求证据。
